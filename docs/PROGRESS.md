### Phase 9 / Task 13 (prompts/13-canonical-ja3-clienthello-capture.md) — Byte-Accurate Canonical JA3 via Raw ClientHello Capture

- **Outcome: investigated in depth, NOT implemented — architecturally impractical without disproportionate complexity and real TLS-handshake-correctness risk.** This task explicitly pre-authorized stopping with a documented blocker rather than forcing a fragile fix if raw ClientHello capture proved impractical; that's the outcome here. **No code was changed** — `compute_fingerprint_from_ssl_object()` remains the production TLS-fingerprint path, unchanged and untouched, and `parse_client_hello`/`compute_ja3` remain implemented, tested, and ready to be wired to a safe capture path if one is ever built.
- **Root cause, verified precisely (not just restated)**: `waffy/proxy/standalone.py` hands its `ssl.SSLContext` to uvicorn, which passes it to `loop.create_server(..., ssl=ssl_context)` — `asyncio`'s selector event loop performs the TLS handshake *inside the transport layer*, consuming the raw ClientHello via OpenSSL before any waffy or uvicorn application code runs. There is no public API to recover those bytes afterward.
- **Two candidate approaches evaluated and rejected, full reasoning in `docs/ARCHITECTURE.md`**:
  1. A parallel raw-socket accept loop using `socket.MSG_PEEK` (the technically-correct nginx-`ssl_preread`-style approach) — requires fully bypassing `loop.create_server(ssl=...)`/uvicorn's own listener and reimplementing the entire connection-acceptance + TLS-upgrade + H11-protocol-handoff sequence uvicorn currently provides. A parallel, independently-correct reimplementation of a security-critical connection path — exactly the kind of undertaking `CLAUDE.md`'s parsing-safety rules and this task's own "don't guess at an approach that silently breaks the TLS handshake" constraint warn against.
  2. `asyncio.BaseEventLoop.start_tls()`'s `StreamReader`-buffer-transfer mechanism (confirmed real by reading CPython 3.14.4's actual `start_tls()` source in this project's test environment — tracked upstream as `gh-142352`) — in principle avoids needing a custom accept loop, but depends on a very recently landed CPython internal with no confirmation it exists on Python 3.12/3.13 (this project's minimum supported version per `CLAUDE.md`), plus reading `StreamReader`'s private `_buffer` attribute (no public peek-without-consuming API exists). Building a security-critical TLS-handshake behavior on an undocumented, recent-only, version-fragile internal was rejected as unsafe — on 3.12/3.13 it would most likely silently drop the ClientHello bytes and break every TLS connection to standalone mode.
- **The "not byte-identical to canonical JA3" caveat from the prior session stands** — this investigation explains precisely *why* it's hard, but does not resolve it. A future attempt should budget for a genuine, carefully-tested custom-accept-loop project (option 1 above), not an incremental addition to the existing `build_ja3_capturing_protocol` subclassing approach.
- **Acceptance criteria run against existing (unmodified) code, all passing** — confirms nothing regressed: `uv run pytest tests/unit/test_session_bot_ratelimit.py -v` (16/16), `uv run pytest tests/integration/ -k tls -v` (2/2: `test_plaintext_mode_tls_signals_absent_no_crash`, `test_standalone_tls_real_handshake_roundtrip`), `ruff check .` clean, `pyright` clean. No new canonical-JA3-in-standalone-mode test was added, since no new capture code exists to test — the existing `test_ja3_computed_from_real_captured_client_hello` (canonical JA3 correctness against a real captured ClientHello, just not one captured *inside a live standalone-mode listener*) remains the relevant coverage, unchanged.
